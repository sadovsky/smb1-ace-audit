# Formal track

Follows `FORMAL_VERIFICATION_PLAN.md`. The question is whether the NTSC/World
*Super Mario Bros.* image can be shown to fetch every instruction from PRG ROM
for every admissible input sequence.

**Status: the primary theorem P1 is not proved and not refuted.** What exists
is a validated machine model, a set of machine-checked local results, and a
decomposition of P1 into named obligations, most of which are open. Every
status below is generated by `python3 -m formal.run` into
`results/manifests/obligations.json`; nothing is entered by hand.

## Scope (M0)

| | |
|---|---|
| Image | iNES SHA-1 `ea343f4e445a9050d4b4fbac2c77d0693b1d0922`, supplied locally, never distributed |
| Cartridge | NROM-256: 32 KiB PRG at `$8000-$FFFF`, no PRG RAM, no registers |
| CPU | Ricoh 2A03 at instruction granularity; decimal flag exists, adder ignores it |
| RAM | 2 KiB, mirrored through `$1FFF` |
| `Fetch(s)` | the start of `cpu.step`: the opcode read of an instruction. Operand reads, the reset-vector read and DMA are not fetches |
| Cold boot | all registers, all flags except I, and all RAM unconstrained; PC = reset vector |
| Warm reset | a transition available at every instruction boundary |
| Controller | every read of `$2000-$7FFF` is an unconstrained byte, so every serial response is admitted, physically realisable or not |
| NMI | may occur at any boundary while the ghost copy of PPU-control bit 7 is set |
| IRQ | may occur at any boundary while I is clear |

`model/devices.py` and `model/transitions.py` say why each abstraction only
adds behaviours, and list the four assumptions that are **not**
over-approximations (`MA-PPU-POWERON`, `MA-PPU-WARMUP`, `MA-NMI-EDGE`,
`MA-CPU`).

## Model validation (M2)

`python3 -m formal.validate_model` compares `model/cpu.py` with two
independent sources. The same definition is used for validation and for
proofs; there is no separate fast interpreter.

| source | compared | mismatches |
|---|---|---|
| SingleStepTests `nes6502` vectors, 300 per opcode, 237 opcodes | 71,100 | 0 |
| py65 on random states, 40 per documented opcode | 6,040 | 0 |
| SingleStepTests, every vector (10,000 per opcode), 237 opcodes (`tools/validate_full.py`) | 2,370,000 | 0 |
| exhaustive over small input domains against the second CPU implementation in `dyn/` (`tools/exhaustive.py`) | 5,915,520 | 0 |

For the seven unstable encodings the full runs check instead that everything
the model fixes agrees (70,000 vectors and 196,608 exhaustive cases admitted);
those are not counted as agreement. The exhaustive run covers, per opcode, the
domains listed in `results/reports/model_exhaustive_equivalence.json`; state
outside each domain is a fixed set of edge values. `JAM` differs from hardware
in one dead field: the vectors advance PC by one, the model leaves it and
halts. Interrupt hijacking (an NMI arriving during `BRK`) cannot be expressed
at instruction granularity.

Not covered, and stated in the report: the six unstable undocumented
instructions (modelled as havoc), the twelve `JAM` encodings, cycle-level
behaviour, and interrupt/reset entry (unit tests only). This is agreement on a
finite sample. It is not a proof that the model matches a console.

## Results

Counts from the manifest: 24 `proved`, 25 `conditional`, 3 `refuted` (all
three are negative tests that are supposed to be refuted), 40
`abstract_counterexample`, 7 `unknown`.

**Proved** (about the model, no assumptions, Z3 and cvc5 agree where a query
exists):

- `L-92C8-ARITH`: `v <= 8` implies `((v or 8) - 1) mod 256 <= 7`.
- `L-92C8-ROM-EXACT`, `L-92C8-ROM`: executing the image's own bytes from
  `$92B0` to the fetch at `$92C8` leaves `A = ((RAM[$071F] or 8) - 1) mod 256`
  for every initial state, so the arithmetic lemma is tied to the program
  rather than to a transcription of it.
- `D-xxxx-CONTRACT`, all 18 dispatch sites: if `(A and $7F)` is inside the
  table when the `JSR $8E04` is fetched, the fetch after the JumpEngine is at
  exactly that table entry, for every stack pointer and RAM content. The frame
  is pushed by the `JSR` inside the query, so frame authenticity is not an
  assumption.
- `LOC-DIRECT`: all 10,370 instruction starts in the graph whose successor is
  fixed by their own bytes have every successor in the graph (exhaustive
  execution of the model). `LOC-ENGINE`: the one `JMP (abs)` is the
  JumpEngine's and it is entered only from the 18 sites. `LOC-ASYNC`: the three
  vectors point into the graph.

Each lemma has a negative twin that drops the precondition (or widens the index
by one) and is refuted with a counterexample, so the checks are not vacuous.

**Conditional** on `J-LOCATION` and `J-ASYNC` (and `J-IRQ` where noted):

- `P6-D2E5-INDEX`, `P6-BDBD-INDEX`: the index is in range at the fetch, from
  the code alone. These are the same two sites the value-set derivation in
  `analysis/` found bounded without a RAM assumption; the two methods share
  only the decoder and the graph.
- `P6-92C8-INDEX-GIVEN-071F`: in range given `RAM[$071F] <= 8` at `$92B0`.
- 22 of the 45 instructions that can write `RAM[$071F]` never store a value
  above 8 there.

**Open.**

- The other 16 site indices are `abstract_counterexample`: from an
  unconstrained state the model reaches the site with an out-of-range index.
  That says the code does not bound the index locally. It does not say the
  game can get there.
- `P6-071F-PP` (`RAM[$071F] <= 8` at `$92B0`) is `unknown`: initialisation is
  open and 23 writers are open. Among them is `DEC $071F` at `$92BF`, which
  preserves the domain only if the dispatched task left the cell alone.
- `LOC-RETURN` (every `RTS`/`RTI` lands in the graph) is `unknown`. No
  shadow-stack invariant has been stated against the transition relation; 61
  of 71 non-push instructions that can address `$0100-$01FF` are not excluded
  by slicing.
- `J-IRQ` and `J-ASYNC` are `unknown`, and every slice-based result assumes
  them.
- `P1` therefore stays `unknown`.

## Why the conditional results are not circular

A slice result has the form "if control arrived along recorded edges, the bad
condition is unsatisfiable". `J-LOCATION` is the statement that control only
arrives along recorded edges, which is P1's own certificate. So these are
conjuncts of one joint induction (plan section 10) and cannot be promoted
one at a time. `Ledger.settle` enforces that: an item is `proved` only if it
has no assumptions and every dependency is `proved`, and a dependency cycle
proves nothing.

## Trusted base and known gaps

- Z3, cvc5 and Bitwuzla. No independently checkable certificate is produced;
  agreement of three solvers is the cross-check.
- Slice-based results are cross-checked too (`verify/crosscheck.py`). Every
  answer the slicer relies on -- the `unsat` that closes a suffix and the
  `unsat` that makes a symbolic PC unique -- is rendered as SMT-LIB with its
  symbols renamed canonically, hashed, counted, and re-asked of cvc5 and
  Bitwuzla in a worker pool. Each obligation's `detail.slice_queries` carries
  the query count, a digest over the distinct query hashes and the per-solver
  tally; a disagreement demotes the obligation to `unknown` and a
  second-solver timeout is reported as one. Identical query texts are
  re-checked once, and both the total and the distinct count are reported.
- Queries that embed image bytes are written as `*.rom.smt2`, which is ignored
  by git so the image is not redistributed; the manifest keeps their SHA-256.
  Slice queries are not written by default -- there are tens of thousands --
  but `SMB1_SAVE_SLICE_QUERIES=1` writes them, and `SMB1_SLICE_QUERY_DIR`
  puts them outside the tree.
- `analysis/cfg.py` for everything that lists `J-LOCATION`. Its *successor*
  relation is now machine-checked against the model, instruction by
  instruction (`GRAPH-EDGES`, `properties/graph_check.py`): for every node
  whose own bytes decide where control goes, the recorded successors are
  exactly the ones `cpu.step` allows from an unconstrained state, and each
  recorded edge is shown feasible. What that leaves assumed is the
  completeness of the predecessor relation for the transfers it excludes --
  `RTS`/`RTI` and the JumpEngine's indirect jump, i.e. `LOC-RETURN` and
  `LOC-DISPATCH`.

## Running

    export SMB1_ROM=/path/to/verified/image
    python3 formal/tools/fetch_vectors.py ~/big/smb1-formal/harte   # optional
    python3 -m formal.validate_model        # about 4 minutes
    python3 -m formal.run                   # about 10 minutes
    python3 -m unittest formal.tests.test_formal formal.tests.test_graph_check

Needs `z3-solver`; `cvc5`, `bitwuzla` and `py65` are used when installed.
Hashing every slice query and re-asking it elsewhere roughly doubles what the
slice modules take. The re-check runs in four worker processes;
`SMB1_CROSSCHECK_WORKERS` changes that, and `SMB1_CROSSCHECK=0` turns it off
-- which every obligation that would have carried a re-check then says.
